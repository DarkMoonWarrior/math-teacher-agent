# ADR：M14 摘要密钥版本与轮换

日期：2026-09-09
状态：M14 当前决策；登录防护和账号生命周期审计已接入，集中式密钥管理尚未实现。

## 背景

正式登录防护和操作者生命周期审计都使用独立 HMAC 隐去账号、网络和操作者线索。直接替换单一密钥会让同一线索产生完全不同的摘要：登录失败次数会被清零，审计记录也无法判断由哪一代密钥生成。批量重写既有摘要不可行，因为存储中没有原始邮箱、IP 或操作者标签，也不应为了迁移重新收集这些值。

## 决策

1. `VersionedHmacKeyRing` 是登录防护与生命周期审计共用的深模块 Interface。调用者只需请求“用当前密钥生成摘要”“生成当前与过渡密钥的候选摘要”或“判断持久化摘要是否属于已配置密钥”；JSON 解析、数量限制、版本格式、指纹和旧格式兼容都留在模块内部。
2. 登录防护和生命周期审计继续使用两套互不复用的密钥环。每套配置包含一个当前 key ID、一个当前密钥和最多三个旧 key ID/密钥。key ID 不是秘密，但必须唯一且永不绑定另一把密钥；密钥至少 32 个字符、相互不同，并只存在于私有部署配置。
3. 新摘要格式为 `k1:<key-id>:<16位密钥指纹>:<64位HMAC>`。指纹只用于发现“同一 ID 被错误地换成另一把密钥”，不能替代密钥；高熵随机密钥仍是前提。旧版 64 位摘要不重写，过渡期继续作为候选匹配。
4. 登录评估会同时统计当前和已配置旧密钥产生的摘要。若保留期内出现版本化摘要，但对应 key ID/指纹已不在密钥环中，登录防护失败关闭；不能通过提前删除旧密钥把失败次数清零。旧登录密钥必须在最后一次使用后至少保留完整的 `production_login_audit_retention_hours`。
5. 生命周期审计的新事件只用当前审计密钥写入，历史事件保持原样。当前只读能力仅聚合动作/结果，不做逐身份关联；旧审计密钥何时销毁必须等待审计保留与受控调查政策，不能由本切片自动决定。
6. `keyring-status` 只验证两套配置并输出当前 key ID 与旧密钥数量，不读取或创建数据库，不输出密钥、摘要、路径或身份。轮换由部署配置和重启完成，没有网页、HTTP 或 Agent 入口。

## 首次升级与轮换顺序

1. 先部署本版本，并让 `v1` 继续使用升级前的原密钥；不要在首次升级时同时换密钥。这样既有无版本摘要仍可由同一密钥匹配，新写入开始带 `v1` 标识。
2. 生成新的高熵随机密钥和从未使用过的 key ID。把旧的 `v1` 密钥加入 `PREVIOUS_KEYS_JSON`，再将新 ID/密钥设为当前值。
3. 在私有部署环境运行 `python -m app.modules.account_identity.operator_cli keyring-status`，确认配置可解析；随后重启应用并检查 `/ready`。命令只做配置预检，不代表存储、代理或分布式限流已生产就绪。
4. 登录旧密钥至少保留到最后一次旧密钥写入后的完整登录事实保留期。过早移除会让 `/ready` 和登录失败关闭。审计旧密钥按独立保留/调查政策处理。
5. 不批量重写、不导出、不反查历史摘要，也不把真实密钥写入命令行、Git、日志、回执或文档。

## 明确未解决

- 当前配置来自进程环境，没有 KMS/HSM、自动轮换、密钥租约、双人审批或集中审计。
- 最多三个旧密钥是过渡实现的有界限制，不是长期审计密钥保管方案；在达到上限前必须先确定审计保留与销毁政策。
- 升级前无版本摘要无法自行证明由哪把密钥生成，所以首次升级必须保持原密钥；该遗留窗口经过登录事实保留期后才消失。
- SQLite 仍不是分布式限流或不可抵赖审计存储；可信代理、共享计数和生产部署仍属下一段。
