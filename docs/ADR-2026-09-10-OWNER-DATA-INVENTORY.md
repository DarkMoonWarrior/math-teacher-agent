# ADR：M14 owner 数据只读清点边界

日期：2026-09-10  
状态：M14 PostgreSQL tenant adapter 第二段的第一切片；清点已实现，迁移尚未开始。

## 背景

正式身份已经把 `account_id`、`tenant_id` 与稳定内容 `owner_id` 分开，但现有私人内容仍分散在多个 SQLite 文件和文件目录中。直接编写批量更新或复制脚本，会遗漏继承父对象归属的子表、无 owner 的旧表和仅能通过数据库引用判断归属的文件，也可能把未知新表静默丢弃。

## 决策

1. 新增独立 `OwnerDataInventory` 深模块，只供本机操作者运行，不接 HTTP、浏览器、Agent 或模型。
2. 清点目录固定列出私人资料、截图识别、个人题库、PDF 导入、教案、试卷和教师记忆的 SQLite 表，以及四类关联文件目录。公共题库、派生索引、导出物、会话、安全事实和 M13 验证事实不混入私人内容迁移。
3. 表归属明确分为：直接含 `owner_id`、通过父对象继承 owner、旧版无 owner。只对直接归属表按操作者指定的源 owner 计数；继承表不得伪造 owner 计数。
4. SQLite 只用只读 URI 和 `query_only` 打开，不创建库、不初始化表、不修复 schema。已知表可按业务模块惰性创建；任何未知表、视图、触发器、缺失关键列、链接或无法读取的对象都失败关闭。
5. 非空文件目录在完成“数据库引用 → owner → 文件”逐文件对账前保持阻塞。不能因为目录位于私人路径就假设其中所有文件属于同一 owner。
6. 输出只含稳定 store/table 名、数量、状态、问题码和报告指纹，不含文件路径、owner 值、行 ID 或内容。报告指纹用于比较两次只读清点，不是迁移授权，也不能替代迁移事务内的一致性检查。
7. 缺失 store 表示没有可迁移对象，不创建空文件，也不阻塞清点。旧版无 owner 表为空时可继续；一旦含行即阻塞，必须先形成明确归属规则。

## 操作者入口

从可导入 `apps/api` 的 Python 环境运行：

```powershell
python -m app.modules.tenant_migration.inventory_cli --source-owner-id owner_teacher
```

退出码 `0` 表示当前清单没有阻塞项，`2` 表示清点成功但发现阻塞项，`1` 表示配置或清点不可用。命令全程只读。

## 尚未完成

- 没有写入 PostgreSQL 内容表，也没有更新任何现有 `owner_id`。
- 没有建立源 owner 到正式账号 owner 的映射，没有逐对象复制、幂等、对账、切换或回滚。
- 非空文件目录仍会明确阻塞；下一切片必须先实现引用清单和逐文件校验。
- 没有连接真实 PostgreSQL，也没有宣称通过 tenant isolation、IDOR 或生产 Gate。
